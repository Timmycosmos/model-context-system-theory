# 命题｜上下文消费者到上下文维护者

## 原句

- AI 幻觉的根源之一，是它把上下文当生成材料，而不是现实边界。
- 成熟 Agent 的方向，是从上下文消费者转变为上下文维护者。

## 解释

这个命题的关键区分在于两种对待上下文的根本态度。

**上下文消费者**的行为模式是单向的：读入上下文 token，经过模型变换，输出下一个 token。上下文对它而言是一堆可供提取语义信号的原材料——用户说了什么、检索回了什么、之前聊过什么。它没有"这个上下文在我说完之后会变成什么样"的概念。事实上，它根本不会在生成之后回头检查上下文发生了什么变化。因为上下文窗口在下一轮请求中是重新灌入的，模型在当前轮次里看不见"未来上下文"。

**上下文维护者**的行为模式不同。它不只看当前上下文的语义内容，还看上下文的结构特征：哪些是用户陈述的事实、哪些是自己刚刚生成的推测、工具调用返回了什么新信息、哪些信息之间存在矛盾、哪些缺口在当前轮次没有被填补。它在回答的同时，为自己消失之后的"下一个自己"准备地基。它的输出不只是生成结果，还包括状态的显式写回——把这一次理解了什么、确认了什么、排除了什么、留下了什么未解决的问题，写进上下文下游能识别的位置。

用一句话总结这个区别：上下文消费者用上下文来生成，上下文维护者把上下文当作需要持续照管的环境。

一个关键观察是：即使在目前没有显式写回机制的工程条件下，很多优秀的 prompt 设计已经在无意识地逼近"维护"——比如在对话结束时让模型总结当前状态、标记未解决的问题、声明不确定性。这说明"维护"不是锦上添花的额外功能，而是上下文系统本来就缺失的一环。

## 推出的结论

**1. 给 AI 更多上下文，不等于让 AI 更负责。**

更多上下文意味着更丰富的语义原材料，但不意味着模型对自己的输出后果承担更多责任。把 10k token 扩到 100k token，增加了信息量，但没有增加任何维护行为。如果没有显式的写回和状态标记，更多上下文只是放大了"材料使用"的规模，而没有让它变成"环境维护"。

**2. RAG、memory、tool use 如果没有写回和治理，仍然只是提供更多材料。**

检索增强生成把外部文档拉进上下文窗口，但模型生成完后，这些文档的引用关系和可靠度标记就消失了。下一轮如果想用到同一批文档，系统必须重新检索——上一轮对哪些文档准确、哪些误导的判断，没有被固化。Memory 系统同理：如果 memory 只是积累而不维护，它会从"跨时间上下文"退化为"跨时间垃圾堆"。

**3. Agent 的关键不是单次回答质量，而是长期上下文状态质量。**

衡量一个 Agent 成熟度，不能只看单次回答的正确率、流畅度、工具调用合理性。要看：在连续 20 轮交互后，上下文中仍然有多少有效事实、出现了多少未解决的矛盾、被幻觉污染的比例、有多少已知缺口被标记过。一个 Agent 的单次回答可能每次都很漂亮，但第五轮开始上下文已经不可靠——这个 Agent 长期来看是失败的。

**4. 输出不是结束，而是未来上下文的种子。**

每一轮输出在下一轮都会变成上下文的一部分。如果不考虑这一点，输出就倾向于"最大化当前流畅度"而不是"最小化未来歧义"。上下文consumer 的生成目标函数是当前轮次的 token 概率，上下文维护者的生成目标函数应该额外包含：减少未来上下文的熵。

## 能解释的问题

**幻觉。** 模型产生与事实不符的陈述，既是因为训练数据和推理的固有局限，也是因为它没有在上下文中标记"以下内容我猜测的/我不确定的/我无法验证的"。没有标记的上下文，下一轮自己读到自己，就会把猜测误认为事实。

**乱承诺。** "我会帮你做 X""我已经完成了 Y"——模型很擅长生成这些句子，因为它们在当前上下文中看起来流畅且礼貌。但它没有核对"自己是否真的具备执行 X 的能力"或"Y 是否真的被完成了"。维护者会在承诺之前检查自身能力边界，并在承诺之后写回一个待办标记。

**假记忆。** 上下文作为一个整体，对"哪些是我自己生成的、哪些是用户给的、哪些是工具返回的"没有结构分化。所有 token 都会被下一轮当作同等地位的输入。维护者需要对这些来源进行分区和标记。

**假反思。** "我仔细想了一下，之前我确实错了"——这句话可能是模型生成的、看起来像反思的 token 序列，而不是任何真实反思过程的结果。上下文维护者的反思应该伴随可追溯的状态变更记录，而不是一句修辞性的"我想了一下"。

**工具调用不负责。** 模型调用了一个工具，拿到了结果，但在生成回答时可能对工具结果做了选择性引用或曲解。它没有义务在下一轮的上下文中保留"我调用了什么工具、返回了什么、我对结果做了什么判断"。维护者需要在工具调用后写回结构化的事实更新。

**长期任务漂移。** 在长达数十轮的任务中，Agent 会逐渐偏离初始目标，因为每一步的上下文都在被前一步的输出微调方向，而没有机制把初始目标锚定并持续比对。维护者需要在每一步检查当前轨迹与初始目标的偏移量。

**记忆污染。** 当模型把大量中间推理、已被否定的假设、错误的检索片段全部留在上下文中时，下游的推理质量会系统性地下降。维护者需要定期清理这些"上下文垃圾"。

## 可能的反对意见

**反对一："这不就是 prompt engineering 吗？"**

回应：prompt engineering 关注的是"用什么指令让模型产生更好的输出"。上下文维护关注的是"输出在成为未来输入时会产生什么结构效应"。前者优化回答质量，后者优化上下文生态。两者工作在不同层面——一个好的 prompt 可以让单轮输出更精确，但它不改变"输出只是用来产出下一轮上下文原材料"这个根本角色。维护是一种架构设计，不是一种指令技巧。

**反对二："模型本来就是生成器，为什么要求它维护上下文？"**

回应：单次调用中的模型确实是生成器。但一个持续运行的 Agent 系统不是单次调用——它是一个循环系统，生成器的每一次输出都成为下一次输入的一部分。当生成器运行在一个循环中，它对循环的长期状态负有隐式责任。我们不是要求"模型"改变它的本质，而是要求"模型—上下文系统"具备维护自身稳定性的机制。

**反对三："只要工具和检索足够好，幻觉不就减少了吗？"**

回应：工具和检索改善的是信息摄入的覆盖面，不是信息在上下文中的管理质量。工具调用本身会产生大量结果，这些结果如果不经判断地堆在上下文里，反而会增加混乱。更准的检索不等于更干净的上下文。维护是信息摄入之后的独立环节——需要对摄入的信息做判断、标记、结构化和清理。

## 工程落点

**上下文维护型 Agent 的最小循环：**

```
用户输入
  → 上下文诊断（当前状态、缺口、冲突、污染度）
    → 事实/假设分离
      → 回答或行动
        → 工具结果解释（如果调用了工具）
          → 写回候选生成（标记本轮确认了什么、排除了什么、遗留了什么）
            → 状态更新
              → 下一轮上下文
```

**核心模块：**

- **上下文诊断器**：在每个轮次开始前，对当前上下文进行健康检查——哪些信息仍然有效、哪些已被推翻、哪些区域的可靠性可疑。
- **事实/假设分离**：显式区分上下文中的"已确认事实""模型推测""用户断言""工具返回结果"四类信息，并以不同标记方案处理。
- **缺口与冲突标记**：主动识别上下文中缺失的关键信息，以及不同来源之间的直接矛盾，生成结构化的缺口/冲突记录。
- **工具结果解释器**：不把工具返回结果直接丢进上下文，而是先做判断——这个结果可靠吗、完整的吗、是否需要交叉验证。
- **写回机制**：将本轮的理解、判断、遗留问题以结构化形式写回上下文，让下一轮自己或下一个模型能从一致的状态出发。
- **记忆卫生**：定期清理不再有效的中间推理、已被纠正的错误结论、已过时的事实引用。
- **输出责任检查**：在输出给用户之前，检查"我是否有能力做出这个承诺""我是否真的完成了这个操作""我对其中哪些部分不确定"。
